# Доноры corpus-core и expert-constructor-core: создание базы знаний и поиск

**Дата:** 2026-11-20. **Метод:** только чтение кода, данных и документов двух проектов; базы
открывались в режиме read-only; ни одного вызова моделей и платных API. Детерминированный код доноров
дополнительно запущен на нашей тестовой книге и на наших 100 вопросах (часть В) — бесплатно, локально,
временные файлы только во временной папке вне репозитория. Ни один файл проектов не изменён;
единственный созданный файл — этот отчёт.

**Пометки зрелости:** **[измерено]** — есть прогон и число; **[реализовано]** — есть в коде, эффект на
вопросах не измерен; **[заявлено]** — написано в документе, кодом не подтверждено; **[идея]** — мой
вывод, в доноре этого нет.

**Про ссылки.** Строки Python-конвейера corpus-core сняты вспомогательным проходом; ключевые (поиск,
индекс, нарезка, инварианты, замеры, счётчики базы) я перепроверил сам. Не перепроверенные помечены
знаком †.

**Сокращения путей:** `ECC/` = `~/Code/expert-constructor-core/bounded_contexts/`;
`CC/` = `~/Code/Доноры/corpus-core/`; `SNAP/` = `~/Code/Доноры/corpus-core/constructor/bounded_contexts/`.

## Главное в восьми строках

1. **Ни в одном из двух доноров нет векторного поиска, графа в поиске, лестницы «лёгкий поиск →
   сильный» и переранжирования моделью.** Не в коде, не в данных. В документах вектор либо назван
   будущей точкой сравнения, либо отклонён сознательно.
2. **Это три разных поисковика, а не два.** Основной ECC ранжирует по пересечению слов без индекса.
   Его снимок внутри corpus-core ушёл дальше: полнотекстовый индекс, лёгкий стемминг, отсев частых слов,
   разбор вопроса дешёвой моделью, поиск по дистилляту. Собственный поиск corpus-core (MCP-сервер) —
   самый слабый: все слова обязательны, стемминга нет.
3. **Промежуточный слой в ECC есть — как контракт и проводка.** Запрос на контекст → пакет контекста →
   трасса. Но круг поиска один, «уверенность» — метка, которая ничего не запускает, модель в поиске не
   участвует.
4. **Самая зрелая часть доноров — создание базы, а не поиск.** В corpus-core это конвейер разметки
   моделью с жёсткой дисциплиной (закрытые списки, решение по номеру, нарезка без потерь, сшивка
   кодом) и слой дистиллята. В ECC — полностью детерминированная упаковка без модели.
5. **Поиск доноры не мерили.** ECC: 6 вопросов на учебном пакете из 6 фрагментов (750 знаков). Снимок:
   14 тестов кода, набора вопросов нет. corpus-core: замера поиска нет вовсе.
6. **Замер на нашей книге [измерено].** Ранкер ECC — 44 из 60, столько же, сколько у нас, но на
   других вопросах. Простой запрос снимка — 54–56 из 60. Тот же простой запрос по нашим же фрагментам —
   54 из 60.
7. **Главная находка — не про доноров [измерено].** 14 из 16 наших промахов — не промах поиска, а один
   отсекающий порог в нашем коде (`apps/telegram-runtime/src/retriever-adapter.mjs:419`). С этим порогом,
   снятым в памяти процесса, наш собственный поиск даёт 58 из 60 при том же окне 12 и нуле вызовов
   моделей. Настоящих промахов поиска — два (Q035, Q060).
8. **Что брать:** принцип «деградация вместо пустоты» (он и закрывает порог), контракт разбора вопроса
   с синонимами и закрытым списком, мелкую нарезку для поиска, дисциплину разметки для офлайн-сборки.
   **Не брать:** ранкер ECC, MCP-поиск corpus-core, поля телеметрии с зашитыми значениями, описания,
   написанные из знаний модели.

# Часть А. expert-constructor-core

## А1. Что это и где

`~/Code/expert-constructor-core`, Node 24+. Четыре модуля (`README.md:39-46`): интерфейс чата,
подготовка базы знаний (KBS), сборщик контекста под вопрос (RCB), ответное ядро (Answer Core).
Замысел — «конструктор экспертов»: партнёр приносит свои материалы, система упаковывает их в пакет
знаний, и эксперт-ассистент отвечает из пакета.

Отдельно лежит большой документ «структура архитектурного ядра»
(`ECC/struktura_architekturnogo_yadra.md`, 995 строк): универсальная самообучающаяся система из 14
малых этапов (§2.3, `:81-107`), база эксперта (§2.10, `:275-307`), слабые места (§12, `:965-991`).
**Слов «поиск», «индекс», «вектор», «граф», «эмбеддинг», «ранжирование», «семантика» в нём нет ни
одного раза** — это документ про роли и обучение, не про доступ к знанию.

## А2. Пайплайн создания базы знаний

Модуль `ECC/knowledge_base_setup/src/` (5 файлов, 3104 строки). **Всё делает код, модель не вызывается
ни разу** [реализовано]: в коде прямо стоит `model_ingestion_status: "not_connected"`
(`sourceAcquisition.mjs:213`), в папке `prompts/` лежит только README.

Этапы:

1. **Приём и нормализация источника** (`sourceAcquisition.mjs`, `sourceNormalization.mjs`). Вход —
   `{source_id, source_name, source_role, text, layer?}` (`packagePublishing.mjs:389-413`).
2. **Диагностика входа и совет, какой сценарий выбрать** (`inputDiagnostics.mjs:261-285`): отдать
   источник целиком / иерархический индекс / чистка с разметкой / «глубокая база». Реализованы первые
   два; остальные — названия.
3. **Нарезка** (`packagePublishing.mjs:489-579`). Новый фрагмент начинается при смене пути заголовков
   или при превышении цели в 260 условных токенов по 4 знака (`:34`, `:36`); выдержка фрагмента — до
   1800 знаков (`:35`). На нашей книге вышло 234 фрагмента, в среднем 698 знаков.
4. **Индекс разделов** (`:581-615`) и **подготовленная библиотека** (`:617-650`). У фрагмента: текст,
   путь раздела, «ключевые слова» — это просто 12 самых частых слов фрагмента (`:1237-1249`), «темы» —
   путь заголовков (`:1233-1235`), слой (роль, политика, надстройка) и слова активации слоя.
5. **Отчёт готовности** (`:680-820`) — только структурные проверки; часть пунктов зашита как
   пройденные (`passed: true`, `:789-801`).
6. **Жизненный цикл пакета** (`:846-879`): карантин / кандидат / активный.

Чего нет: понятий и словаря, синонимов, связей между фрагментами, графа, кластеров, эмбеддингов,
описаний фрагмента моделью.

Что реально собрано [реализовано]: в `~/.local/share/expert-constructor-core/knowledge_base_setup/packages/`
лежат пакет на 237 фрагментов из одного источника (медиана 792 знака) и пакет «менеджер партнёров» на
133 фрагмента из 7 источников со слоями. Тесты модуля есть (5 файлов), мной не запускались — `not_run`.

## А3. Путь запроса и промежуточный слой

Промежуточный слой здесь — пара «ответное ядро + сборщик контекста». Ядро не ищет само, оно просит
контекст по контракту.

1. **Запрос на контекст.** Ядро собирает: вопрос, краткую память диалога, идентификатор пакета, бюджет
   12 000–15 000 условных токенов, цель `answer_user_question`, политику `source_grounded`, бюджет
   времени 1500 мс (`ECC/answer_core_runtime/src/retrievalContextAdapter.mjs:8-40`, `runtime.mjs:31-32`).
   Профиль пользователя в поиск не идёт: «влияет на форму ответа, но не на retrieval»
   (`HANDOFF_PROMPT_RU.md:96`).
2. **Выбор маршрута по размеру** (`ECC/retrieval_context_builder/src/retrievalContextBuilder.mjs:319-360`):
   источник один и не больше 50 КБ (`:7-8`) — отдать целиком; иначе искать по фрагментам. Других
   критериев нет.
3. **Сборка пакета** (`:521-640`): слова вопроса (`:770-792`; память диалога подмешивается только к
   коротким и уточняющим вопросам, `:794-810`) → проверка смены темы (общих слов меньше 18 % — кеш не
   использовать, `:840-855`) → кеш сессии на 5 минут (`:6`) → упреждающие кандидаты (`:879-910`) →
   ранжирование → отбор в бюджет (`:1017-1037`) плюс обязательные якоря слоёв (`:1053-1084`) →
   уверенность → пакет со статусом `ready` или `not_found`.
4. **Ранжирование** (`:912-956`). Индекса нет: в памяти перебираются все фрагменты, для каждого
   считается пересечение множеств слов. Веса: текст ×1, ключевые слова ×0,6, раздел и темы ×1,5, слова
   активации ×0,8. Редкие слова весят больше (`:971-995`). Балл = 0,45 + 0,05 × взвешенное пересечение
   + 0,15 × покрытие + надбавки по 0,08, не выше 0,99. Нет общих слов — ноль. Если в вопросе есть
   «сильные» слова, фрагмент без них отбрасывается (`:958-969`).
5. **Приведение слов к основе** (`:821-838`) — пять зашитых основ: эпиграф, раздел, выбор, налог,
   льгота. Все остальные слова сравниваются буква в букву: «повышение» и «повысят» — разные слова.
6. **Ответное ядро** (`ECC/answer_core_runtime/src/runtime.mjs:17-167`): один вызов поиска (`:57`) →
   слияние свежего и упреждающего пакетов (`contextPackMerge.mjs:27-85`) → решение
   (`answerDecision.mjs:5-36`): уточнить, если вопрос короче 4 знаков или расплывчат; «недостаточно
   контекста», если пакет не готов или контекста меньше 80 знаков; иначе отвечать → сборка ответа →
   лексическая проверка опоры каждого утверждения (не меньше 2 общих слов и 34 % покрытия,
   `groundingEvaluator.mjs:3-5`) → событие обратной связи с меткой (`feedbackEvent.mjs:17`, `:51-58`).

**Что слой делает сам:** выбирает маршрут по размеру, ранжирует, режет в бюджет, ставит уверенность,
перечисляет пробелы, пишет трассу с причиной выбора каждого фрагмента. **Чего не делает:** не
переформулирует вопрос, не ходит за контекстом второй раз, не вызывает модель, не рассуждает о том, что
искать. В `ANSWER_FLOW.md:22` среди решений ядра записано «запросить больше контекста» — в коде такой
ветки нет [заявлено].

## А7. Что стоит перенести в AIchatTG и что не стоит

**Стоит:**

- **Параметр мелкой нарезки для поиска** — около 700 знаков по границам заголовков
  (`packagePublishing.mjs:34-36`, `:489-579`). Сам код не нужен: мы режем в Python в `~/Code/allcourses`.
  Переносится идея «искать по мелким кускам, отдавать крупные». Основание — часть В: при одном и том же
  простом запросе нужная глава первой в выдаче у 40 вопросов из 60 на мелких кусках против 34 на наших.
  [измерено на уровне «задета нужная глава»]
- **Проверка опоры ответа после генерации** (`groundingEvaluator.mjs`, около 100 строк, без
  зависимостей) — как бесплатная метка в журнал. К поиску не относится, приоритет низкий. [реализовано]

**Не стоит:**

- **Ранкер RCB.** На нашей книге он не лучше нашего (44 из 60) и заметно хуже простого полнотекстового
  запроса (54–56). Пять зашитых основ слов — не стемминг.
- **Контракт пакета и трассы.** У нас он уже есть и богаче: статус, уверенность, пробелы, причина
  выбора (`packages/telegram-core/src/retrieval.mjs`).
- **Маршрут «источник целиком».** Вариант «всю книгу в контекст» владелец отверг; наша книга (166 тыс.
  знаков) под порог 50 КБ и не попадает.
- **Упреждающие пакеты и слияние свежего с упреждающим.** Усложнение без единого замера.

## Б2. Пайплайн создания базы знаний

Порядок задают `CC/bin/collect.sh`, `bin/refresh-theme.sh`, `bin/wiki.sh` †:

1. **Адаптеры источников** приводят вход к одному формату (`bounded_contexts/source_ingest/src/` †).
2. **Расшифровка и распознавание** — речь `whisper-1`, картинки `gpt-4o-mini` (`scripts/transcribe_lib.py:23` †,

   `fts5(shortcode UNINDEXED, username, caption, body, text)` — без настройки разбора слов, то есть без

4. **Курирование моделью** (`scripts/curate.py`): относится ли запись к теме, оценка 0–1, причина.

5. **Фасеты** (`scripts/analyze.py` †): 17 измерений (место, еда, храм и т. д.) плюс маршруты

## В3. Что из этого следует

**1. Четырнадцать из шестнадцати наших промахов — не поиск, а порог.** В строках точки отсчёта у этих
14 вопросов статус пакета `not_found`, совпадений со словарём понятий — 0, при этом полнотекстовый
поиск нашёл кандидатов (у Q041 — 11). Их отбрасывает одно условие:

```
apps/telegram-runtime/src/retriever-adapter.mjs:419
if (!run.conceptMatches.length && run.strongUnits < NO_CONCEPT_MIN_UNITS) { ... not_found }
```

с константами `NO_CONCEPT_COV_MIN = 0.60` и `NO_CONCEPT_MIN_UNITS = 2`
(`packages/telegram-core/src/retrieval.mjs:34-35`). Смысл условия: если в вопросе нет ни одного понятия
словаря, выдача сохраняется, только когда не меньше **двух** записей покрывают вопрос сильно. Комментарий
в коде объясняет замысел: такой вопрос «почти наверняка вне домена». Для книги условие устроено против
цели: у вопроса с одной золотой записью сильно покрывающая запись по определению одна. Распределение в
точке отсчёта: все 14 пакетов `not_found` — это «понятий 0, сильных записей меньше двух», и все 14 —
промахи; остальные два промаха (Q035, Q060) — пакеты с 11–12 фрагментами без нужной записи.

**2. Проверка прямым прогоном.** Тот же скрипт, та же база, окно 12, одна константа изменена в памяти:

- порог «не меньше одной сильной записи» — 49 из 60;
- порог снят — **58 из 60**, ложных отказов 0 из 60 (было 14), конфликтные 25 из 30 (было 24).

Это сходится с двумя соседними отчётами этой папки, которые пришли к 58 из 60 другими путями: простой
запрос плагина по нашему индексу (`donor-kb-plugin.md:232-246`) и вектор на пустой выдаче
(`vector-experiment.md:257`). Три разных «вторых шага» дают одно число — значит, дело не в том, каким
шагом искать повторно, а в том, чтобы не выбрасывать найденное. Уточнение к соседнему отчёту: в режиме
поиска кандидатов обнуляет именно строка `:419` ретривера — маршрутизатор домена поиск уже не
останавливает (`apps/telegram-runtime/src/knowledge-retrieval.mjs:114-121`).

шаг. Проверено только на уровне поиска; качество ответов на этих вопросах — `not_run` (нужен платный
прогон).

**4. Гипотеза «качество ограничено архитектурой поиска» на этом наборе подтверждается для 2 вопросов из
60, а не для 16.** Настоящие промахи поиска — Q035 («хочу начать своё дело, но жду, пока накоплю денег
и связей») и Q060 («почему если я крутой специалист, это не гарантирует, что меня повысят»). Q060 не
находит ни один из вариантов — это и есть вопрос другими словами. Плюс конфликтные: 5 из 30 без второй
стороны при окне 12, 2 из 30 при окне 20.

**5. Ранкер ECC переносить незачем:** 44 из 60, нужная глава первой у 20 вопросов — хуже простого
запроса с порядком `bm25` (34–40).

**6. Мелкая нарезка даёт ту же находимость при меньшем контексте.** Вариант B с 8 кандидатами — 54 из
60 при 6,2 тыс. знаков; вариант C с 12 — те же 54 при 36,8 тыс. знаков. Нужная глава первой — 40 против
34. Для цены ответа это заметно: контекст меньше в несколько раз.

## В4. Ограничения замера

- **Критерий мягкий.** Золото размечено на уровне записи-главы. «Глава задета» не значит «найден нужный
  абзац»: кусок в 700 знаков из нужной главы может не содержать ответа, а наш кусок в 2,8 тыс. знаков
  несёт заметную часть главы. Поэтому вывод 6 — про находимость главы, а не про качество ответа.
  Случайный уровень 21–32 из 60 показывает то же самое.
- **Порядок в нашей выдаче** я принял за порядок ранга (столбец «первой / в первых трёх» для наших
  строк) — не проверено по коду.
- **Числа первой версии зеркала книги** (222 фрагмента) в таблицу не включены; на ней после
  собственного ранкера снимка выходило на 1–2 вопроса меньше, чем по кандидатам индекса (54 против 56).
- **Немонотонность:** при снятом пороге окно 20 даёт 57, окно 12 — 58. Один вопрос теряется при
  расширении — похоже на эффект отбора с разнообразием, причина не разобрана.
- **Один корпус, один набор вопросов.** На курсе результат может быть другим.

## Г2. Шесть ожиданий владельца — что нашлось в этих двух донорах

1. **Сравнение архитектур** — таблица выше.
2. **Векторный поиск** — нет ни в одном. В ECC — строка в списке будущих сравнений; в corpus-core —
   письменный отказ.
3. **Адаптивный поиск «лёгкий → сильный»** — нет. Есть выбор по размеру источника и расширение области
   при пустом результате.
4. **Графы** — в поиске нет. В corpus-core граф «пост → объект → маршрут» есть в данных и обслуживает
   отдельные инструменты, а не поиск.
5. **Промежуточный слой** — есть. В ECC это контракт и проводка без рассуждения. В снимке — один шаг
   рассуждения: разбор вопроса дешёвой моделью перед поиском.
6. **Отдельный пайплайн создания базы** — есть в обоих, и это самая зрелая их часть.

Итого по этим двум донорам: из шести ожиданий в коде есть два с половиной (сборка базы, промежуточный
слой, частично — адаптивность как запасные уровни). Вектора, графа в поиске и усиления поиска здесь
нет; если они есть, то в других проектах.

## Приложение. Как повторить замер

Все прогоны — локальные и бесплатные. Временные скрипты лежали во временной папке сессии и могут быть
очищены; ниже достаточно, чтобы собрать их заново.

**Наш поиск с изменённым порогом, без правки файлов.** Скрипт `scripts/eval/ask-offline.mjs` в режиме
`--mode retrieval` (Node 20), пакет `output/eval/tcr-book-v4/packages/tcr-59025ab82058`,
`--max-entries 12 --max-context-tokens 8000`, вывод — в постороннюю папку через `--out`. Константа
подменяется загрузчиком модулей Node (`--import` файла с `module.register`): в функции `load` для
адреса, оканчивающегося на `/telegram-core/src/retrieval.mjs`, строка
`export const NO_CONCEPT_MIN_UNITS = 2;` заменяется на нужное значение (0 или 1) в тексте модуля до его
исполнения. Файл на диске не меняется.

**Код доноров на нашей книге** (Node 24, ключи моделей убраны из окружения):

- вариант A: `buildKnowledgePackageArtifacts` из `ECC/knowledge_base_setup/src/packagePublishing.mjs`
  (чистая функция, на диск не пишет) по 20 файлам `output/eval/tcr-book-v4/mirror/*.md`, затем
  `buildRetrievalContextPack` из `ECC/retrieval_context_builder/src/retrievalContextBuilder.mjs` на
  каждый вопрос;
- варианты B и C: временная база SQLite с таблицами `posts` и `posts_fts` (схема из
  `SNAP/theme_package_adapter/src/themeDescriptor.mjs`), строки — мелкие фрагменты KBS либо наши
  фрагменты из таблицы `chunks` пакета; затем `loadPreparedLibrary` из
  `SNAP/theme_package_adapter/src/sqlitePreparedLibrary.mjs` с `parsedQuery: null` и нужным
  `candidateLimit`;
- вопросы и золото — `output/eval/tcr-book-v4/tcr-book.gold.jsonl`; вид вопроса — по числу золотых
  записей (0, 1, 2).
