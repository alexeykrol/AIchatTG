## 2. Разбор существенных находок

### 2.1 founder-pipeline: карточки, указатель, достаточность

Ближе всего к нашему стеку: файлы `.mjs`, хранение в SQLite.

**Сборка базы.** Модель размечает каждый кусок и возвращает краткое содержание, темы, факты, сущности, связи и
до восьми карточек поиска с полями «вопрос, на который отвечает», «краткий ответ», «тема», «цитата из
источника» (`src/intelligentPipeline.mjs:59-96, 568`). Из разметки код строит указатель трёх уровней: карточка
документа, карточки разделов, карточки кусков со ссылками на соседей (`src/semanticIndex.mjs:3-145`).

**Поиск.** Вопрос сравнивается с полями карточек, у каждого поля свой вес: тема 3.2, ответ 2.5, вопрос 2.2
(`src/services/fastContextRetrieval.mjs:485-546`). Потом открывается точное место источника с соседними кусками
(`src/sourceOnDemand.mjs:1-47`). Отдельный шаг решает, достаточно ли найденного, и запрещает уверенный ответ по
«похожему, но не тому» (`ANSWER_MICRO_PIPELINE.md`, `src/knowledgeAnswerPipeline.mjs:258`).

**Измерено:**

- Указатель с чисто словесным сравнением: 5 из 12 (`INDEX_INFRASTRUCTURE.md:93`). С модельным разбором вопроса
  и модельной проверкой достаточности: 12 из 12 (`INDEX_INFRASTRUCTURE.md:120`). Один урок, 12 вопросов.
- Поиск по карточкам: 20 из 20, 102 мс, ноль вызовов модели, 55 документов, 938 карточек
  (`FAST_CONTEXT_RETRIEVAL.md:669-682`).
- Узкое место полного ответа — сочинение ответа (9,2 с), а не поиск (0,1 с) (`README.md:277-292`).
- Цена разметки: 8 кусков — 31 230 токенов, 0,32 доллара (`BASELINE_COMPARISON_EXPERIMENT.md`, раздел First Run).

**Оговорки к цифре 20 из 20:**

- В коде зашиты ручные подкрутки под этот курс: надбавка за слово «офер» и готовые расширения запроса
  (`fastContextRetrieval.mjs:548-562, 630-643`).
- Перефразировок в наборе не было, они стоят в плане (`FAST_CONTEXT_RETRIEVAL.md:713`).
- Сравнение слов там слабее нашего: точное совпадение и вхождение подстроки, без основ слов (`:653-684`).

Переносить стоит форму данных и шаги, а не код подсчёта баллов.

**Про вектор** в документах проекта сказано прямо: применять к карточкам и единицам знания, а не к сырым
кускам, и только как измеряемую дорожку, которая обязана побить словесную (`FAST_CONTEXT_RETRIEVAL.md:558-584,
721-722`). В коде вектора нет.

### 2.4 Два образца поиска по смыслу

**Плагин поддержки (PHP).** `Архив/ai-support-chat-plugin/includes/class-sqlite.php:63-118`: векторы лежат
текстом в колонке SQLite, близость считается перебором всех строк, порог 0,75, берётся семь лучших. Модель
`intfloat/multilingual-e5-small`, 384 числа (`class-embed.php`). Вектор там запасной путь: основной — один
дешёвый вызов, который относит вопрос к кейсу из закрытого списка (`class-router.php:8-20`). Живая версия
плагина — в `~/Code/alexeykrol-wp` (вне этого обхода).

**Посты (Python).** `Доноры/posts/scripts/build_relations.py:74-112`: локальная многоязычная модель через
`sentence-transformers` — вот для чего пакет стоит в `posts/.venv`. Текст для вектора — заголовок плюс первая
тысяча знаков. Это связи между постами, а не ответ на вопрос.

Замеров качества нет ни там, ни там.

### 2.5 Графы: строятся в четырёх местах, при ответе по ним нигде не ходят

- `graphify` в `ai_lms/.../producer/tools/graphify/` — сторонний пакет. Вход в граф — совпадение слов вопроса с
  названиями узлов, дальше обход на три шага; на перефразировке он не находит стартовый узел. Его замеры — про
  экономию токенов на чужом корпусе (со слов помощника).
- Граф «проблема → решение» из расшифровки (`p1_transcript/stages/knowledge_graph.py`) — для просмотра человеком;
  связи между проблемами ставятся по трём общим словам.
- Связи понятий из п. 2.3 — типизированные, с обоснованием; потребителя нет.
- `strategy/processed-db` — типизированные рёбра между заметками; `ask.py` показывает связи между найденным.

Полезная идея из графа «проблема → решение»: читатель спрашивает языком своей проблемы, а не языком книги.

## 4. Что взять в первую очередь

Оценки трудозатрат грубые. Порядок — по тому, насколько прямо шаг бьёт в «вопрос другими словами» и сколько
нового он тянет в рантайм.

1. **Карточки поиска в индекс (2–3 дня).** Офлайн на Python модель пишет для каждого куска книги вопросы, на
   которые он отвечает, краткий ответ и тему; поля кладутся в FTS5 с весами. Образец схемы —
   `founder-pipeline/.../src/intelligentPipeline.mjs:59-96`. К этому же шагу — «проблемы читателя, на которые
   отвечает кусок» (идея из п. 2.5). Отвечать по-прежнему по исходному отрывку (п. 2.2). Новых зависимостей в
   рантайме нет. У донора на перефразировках не мерилось — проверять на наших 60.
2. **Выбор раздела моделью при слабом результате (1–2 дня).** Дешёвая модель читает короткие карточки разделов
   и выбирает из закрытого списка, куда смотреть. Это и есть «лёгкий поиск → сильнее». Основание: 5 из 12 → 12
   из 12 у донора (один урок) и рабочий маршрутизатор плагина поддержки.
3. **Синонимы понятий (1–2 дня).** Взять промпт и проверку из `ai_lms/.../knowledge_extraction/`
   (`extract_concepts.md`, `validator.py`), пополнить ими словарь понятий. `stage.py` целиком не брать: он
   привязан к своему проекту.
4. **Проверка достаточности и открытие соседних кусков (1 день).** `sourceOnDemand.mjs` — 86 строк, уже `.mjs`.
5. **Вектор по карточкам, а не по сырым кускам (2–4 дня плюс решение владельца).** По собственным критериям
   владельца порог пройден: провал измерен, и он именно на перефразировках. Векторы базы считаются офлайн на
   Python (образец — `posts/scripts/build_relations.py`), хранятся в SQLite, близость считается перебором в
   Node (образец — `class-sqlite.php:75-118`; на объёме книги это миллисекунды). Слияние со словесной выдачей
