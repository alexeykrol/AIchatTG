Пометки зрелости:
- **[измерено]** — число получено из кода или данных, указано, где лежит замер;
- **[мой прогон]** — измерено мной бесплатным повтором поиска донора на его же журналах (метод — в конце);
- **[реализовано]** — есть в коде, работает;

## Главное в семи строках

1. Поиск донора — тот же лексический поиск, что в плагине kb, плюс основы слов и надбавка за понятия.
   Векторов нет (исключены спецификацией), граф на деле не участвует. [реализовано]
2. Ответ на главный вопрос: провалы бота — это **не «поиск не нашёл» и не «нашёл, но модель не использовала»**.
   Это третье: поиск вернул номер нужной записи, но модели показали из неё 1–2 предложения (до 320 знаков),
   нужного места среди них не было, а запись целиком модель не открыла. Так устроены 11 из 14 провалов
   (без одного сбойного хода); настоящих промахов поиска — 3; случаев «место было перед моделью, а она
   ошиблась» — 0. [мой прогон]
3. Когда нужное место оказалось перед моделью, ответ верен в 77 случаях из 78 (два прогона по 60 вопросов);
   когда не оказалось — в 21 из 41. Та же картина в четырёх других прогонах, включая OpenAI. [мой прогон]
4. Сниппет не годится как доказательство: если нужная запись найдена, показанные цитата и резюме содержат
   нужное место только в 25% случаев, и увеличение цитаты ничего не даёт. [мой прогон]
5. Профили ответа (усилие low, лимит 150 слов) вдвое сократили открытия записей и опустили результат на тех
   же 100 вопросах с 83 до 69. Поиск они не трогают — они отбивают у модели охоту читать. [мой прогон]
6. Наращивание силы поиска существует только как право модели: искать ещё и открывать запись она решает
   сама. Кодового критерия «найдено достаточно» нет; «в книге нет» объявляется после одного поиска. [реализовано]
7. Ранжировщик самого плагина (Generic) на уровне записей не лучше донорского. 60 из 60 у Generic даёт не
   функция поиска, а то, что вокруг неё: модель читает записи целиком. [мой прогон]

## 2. Пайплайн создания базы знаний

Сам донор базу не строит: он получил готовую коробку из плагина kb и открывает её только на чтение
(`PLAN.md:74`, `HANDOFF.md:20`, `SPEC.md:286`). Строил её плагин — проект `~/Code/BestMentor_Plugin`, ассет
`assets/tcr/`. Подробный разбор сборки — в соседнем отчёте `donor-kb-plugin.md`; здесь только то, что влияет
на поиск.

**Шаги сборки** [измерено: `~/Code/BestMentor_Plugin/assets/tcr/status.json`, вся сборка заняла 3 мин 22 с,
2026-11-09 18:21:44 → 18:25:06]:

1. `scan` — 12 файлов глав `CH-01.md … CH-12.md` из `~/Code/tcr/chapters` (`kb.yaml:2`).
2. `extract` — код режет главы на единицы не длиннее 12 000 знаков (`kb.yaml:8`, `max_unit_chars`): вышло
   20 единиц. Это не смысловая нарезка, а «глава пополам».
3. `batch-plan` → три пачки (8, 6 и 6 единиц).
4. Чтение пачек моделью — агент `kb-reader`, модель `sonnet` (`agents/kb-reader.md:5`): на каждую единицу
   категория, подтема, жанр, признак «есть практический шаг», резюме 20–500 знаков и понятия с весом
   (`assets/tcr/batches/b01.prompt.md`).
5. Связи — агент `kb-tagger`, модель `sonnet` (`agents/kb-tagger.md:5`). Он **не читает тексты**: работает
   только с карточками (дата, категория, резюме, понятия) — `assets/tcr/batches/e01.prompt.md:5`.
6. `build` — код собирает SQLite с проверками.

**Что получилось** [измерено: `kb/tcr-book/kb.sqlite`, только чтение]:

| Показатель | Значение |
|---|---|
| Записей | 20 (12 глав, большинство разрезаны на 2 части) |
| Объём текста | 165 539 знаков; запись от 294 до 11 917, в среднем 8 277 |
| Названия записей | только «CH-05 (часть 1/2)» — слов по теме в названиях нет |
| Резюме | 153–418 знаков на запись |
| Понятий | 28; привязок к записям 91 (вес 2 — 40, вес 1 — 51), 3–6 на запись |
| Связей | 20: `continues` 8 (часть 1 → часть 2 той же главы), `develops` 11, `applies` 1 |
| Связей `contradicts` | **0** |
| Таблицы плагина `conflicts`, `verdicts`, `misses` | пустые |

**Три свойства этой базы, которые определяют поведение поиска:**

- **Крупная нарезка.** 20 записей по 8 тысяч знаков. Найти «запись» легко (их всего 20), но запись — это
  3–5 тысяч токенов текста, и нужное место в ней занимает около 130 знаков (медиана длины золотой цитаты —
  132 знака) [мой прогон].
- **Пустые названия.** В формуле ранжирования название весит в 5 раз больше текста и даёт надбавку +0,3
  (`search.py:166, 195`), но в названиях нет ни одного слова по теме. Эти веса не работают. [измерено]
- **Противоречий в графе нет.** Разметчик связей видел только резюме по 150–400 знаков; расхождение двух
  мест книги из резюме не видно. Поэтому инструмент возвращает агенту пустой список `contradictions` всегда
  (0 случаев на 153 поиска в журнале) [мой прогон].

## 3. Путь запроса: шаги поиска и агентный цикл

### Шаг 0. Маршрутизатор пишет поисковый запрос

Дешёвая модель (Haiku) решает, нужна ли база (`kb_needed`), и переписывает вопрос в набор ключевых слов
`kb_query` (`src/mentor/pipeline/router.py:43–44, 104–107`; `prompts/router.md:12–14`). При сбое
маршрутизатора — запасной маршрут (`router.py:123–132`).

### Шаг 1. Предпоиск: код кладёт три записи в контекст

До запуска агента код сам ищет по `kb_query` и берёт **три** лучшие записи: `KB_CONTEXT_HITS = 3`
(`src/mentor/pipeline/context.py:36`, вызов :249). В контекст каждая попадает одной строкой:
`- id | название | резюме до 300 знаков | quote: «…»` (:254), под шапкой «…Cite them by id with a verbatim
quote; use kb_search or kb_unit for more.» (:164–165). Общий потолок контекста — 6000 токенов
(`config.yaml:35`).

### Шаг 2. Функция поиска (`search_box`, `src/mentor/kb/search.py:129–188`)

1. Вопрос → слова длиной от 4 букв без стоп-слов (`MIN_TERM = 4`, :35; список :22–32) → основы слов
   (Snowball для русского и английского, «ё» → «е»; `stemming.py`).
2. Два индекса, из каждого берётся `limit × 4` кандидатов (:146, :149):
   - свой индекс по основам `kb_fts`: запрос `"основа1" OR "основа2" …` (:193), веса полей
     `bm25(…, 5.0, 3.0, 1.0)` — название ×5, резюме ×3, текст ×1 (:195);
   - индекс самой базы `units_fts` без основ: слово без двух последних букв (минимум 4 буквы) со
     звёздочкой, тоже через OR (:204), те же веса (:206).
3. Текстовая оценка = оценка по основам + 0,25 × оценка по префиксам (:154), нормируется по лучшей записи.
4. Плюс 0,5 × оценка по понятиям (:161). Понятие считается задетым, если не меньше половины слов его
   названия есть в вопросе; запись получает долю совпадения × вес привязки (:213–229).
5. Плюс 0,3, если основа из вопроса есть в названии (:166); плюс 0,2, если пользователь отметил запись
   ценной (:168); скрытые пользователем записи убираются (:175–177).
6. Берутся лучшие `limit` записей. Соседи по графу добавляются **только если остались свободные места**
   (`if neighbours and hits and len(hits) < limit`, :180–181): связи двух верхних записей, оценка — половина
   от исходной (:274–293).
7. Противоречия — связи типа `contradicts` между найденными записями (:184).
8. Цитата: `best_passage` (:91–126) выбирает одно или два соседних предложения с наибольшим числом слов
   вопроса, не длиннее `quote_max_lines × 160` = 320 знаков (`config.yaml:32`, `search.py:36`).

Параметры по умолчанию: `kb.limit: 6`, `kb.quote_max_lines: 2`, `kb.neighbours: true` (`config.yaml:31–33`);
`limit` из запроса агента ограничен диапазоном 1–20 (`service.py:55`).

### Шаг 3. Что получает агент от `kb_search` (`src/mentor/kb/tools.py:42–68`)

На каждую запись: `id`, название, резюме до 400 знаков (:52), цитата, дата, категория, способ попадания
(`via`), вердикт. Весь список записей ограничен 6500 знаками (`RECORD_BUDGET`, :19, :54). Дополнительно:
определения понятий до 200 знаков (:62), до 12 связей (:63), до 6 противоречий (:64). Если ничего не
найдено — подсказка «Nothing found: rephrase once; if still empty, say the box has no answer.» (:67).

Итого после поиска модель видит по каждой записи **максимум 320 знаков текста книги** и резюме. Текста
записи в выдаче нет.

### Шаг 4. Агентный цикл

- Агент — Claude Agent SDK без встроенных инструментов (`src/mentor/runtime/sdk.py:152–154`), до 12 шагов
  модели на ход (`config.yaml:22`, `sdk.py:161`), усилие берётся из профиля (:164).
- Может: искать ещё (`kb_search` со своим запросом и своим `limit`), открыть запись (`kb_unit`: без `full` —
  первые 1500 знаков, с `full=true` — весь текст; `service.py:89, 104`), посмотреть понятие (`kb_concept`),
  записать пробел (`kb_miss`).
- Любой ответ инструмента обрезается на 12 000 знаков с пометкой `[truncated]`
  (`src/mentor/runtime/tools.py:29, 165–166`).
- После ответа код проверяет цитаты и один раз просит переписать (`turn.py:288–325`) — разобрано в прошлом
  досье.

### Шаг 5. Что промпт говорит про поиск (`prompts/system.md:44–73`)

- Искать в базе до ответа; в контексте уже могут лежать `<kb_results>` (:46–47).
- Каждое утверждение подкреплять цитатой с id.
- «Say when absent»: если ответа в базе нет — сказать это первой фразой, записать `kb_miss` и **не собирать
  ответ из слабо связанных записей** (:60–64).
- «Show conflicts»: если записи расходятся — сказать об этом в начале (:67–71).

Чего в промпте **нет**: требования искать второй раз, переформулировать запрос, открывать запись перед тем,
как объявить «в книге нет».

### Чем это отличается от «Generic + плагин kb»

| | Бот донора | Generic (Claude Desktop + плагин) |
|---|---|---|
| Ранжирование | bm25 по основам + префиксы + понятия + название (`search.py:129–188`) | bm25 по префиксам, без основ и понятий (`reference/kb-plugin/search.py:159–204`) |
| Записей за поиск | предпоиск 3, поиск агента 6 | 8 (`reference/kb-plugin/search.py:519`) |
| Сниппет | 1–2 предложения, до 320 знаков | около 18 слов (`snippet(…, 18)`) |
| Кто запускает поиск | код (предпоиск) + модель по желанию | только модель, по инструкции навыка |
| Правило повтора | «переформулируй один раз, если пусто» (`tools.py:67`) | то же (`reference/kb-plugin/SKILL.md:44–47`) |
| Чтение записи целиком | `kb_unit full=true`, обрезка на 12 000 знаков | `S --unit <id> --full`; в коде плагина обрезки нет (`reference/kb-plugin/search.py:207–218`) |
| Модель и усилие | Sonnet, усилие low, лимит 150 слов (96 ходов из 100) | не записано (`evals/baseline/questions.md:9–11`) |
| Вопросы | по одному, каждый в новом диалоге (100 ходов = 100 диалогов в журнале) | порциями по 10–20 в одном чате (`questions.md:11`) — прочитанные записи остаются в контексте для следующих вопросов |

Вывод по таблице: функция поиска у бота не слабее (см. п. 5.11). Разница — в двух нижних строках и в том,
сколько текста книги реально доходит до модели.

## 4. Адаптивность: есть ли наращивание силы поиска

**Лестница есть, критерия нет.** [реализовано]

Ступени, которые существуют в коде:

1. переформулировка вопроса маршрутизатором (`router.py:104–107`);
2. предпоиск кодом, 3 записи (`context.py:249`);
3. собственный поиск агента с любым запросом и `limit` до 20 (`tools.py:95–110`);
4. чтение записи целиком (`kb_unit full`);
5. просмотр понятия со списком записей (`kb_concept`).

Переход со ступени на ступень решает **только сама модель**. В коде нет ни одной проверки «найдено
достаточно», ни обязательного второго поиска, ни обязательного чтения записи. Единственный кодовый сигнал —
подсказка при пустой выдаче (`tools.py:67`), и она **не срабатывает никогда**: запрос собран через OR, и
типичный вопрос задевает 17–20 записей из 20. Пустых выдач — 0 из 153 поисков в основном прогоне и 1 из 208
в прогоне без профилей. [мой прогон]

Как модель пользуется этим правом при усилии low [мой прогон, `data/eval/exp-baseline-bot.sqlite`]:

- в 42 из 60 вопросов с ответом агент не сделал ни одного собственного поиска;
- запись целиком открыта в 25 из 60;
- `kb_miss` («в книге нет») записан в 14 ходах: в 12 — после одного поиска, в 2 — вообще без собственного
  поиска, и **ни разу** перед этим не была открыта запись.

То, что донор сам собирался сделать и не сделал [заявлено, `BACKLOG.md:19–26`]: «A "no answer" reply must
follow a second search», цель — не меньше 55 из 60. Работы не начаты.

Критерий «достаточно», который следует из замеров (п. 5.4): достаточно — когда перед моделью лежит само
место с ответом, а не номер записи и её резюме. [идея]

### 5.2. Мой разбор журналов: метод в двух словах

журнале (в 5 ходах предпоиска не было). Затем для каждой золотой цитаты проверил, была ли она в тексте,
показанном модели: в сниппетах, в резюме или в открытой записи (с учётом обрезки на 12 000 знаков). Место
считается показанным, если не меньше 60% слов цитаты идут подряд в показанном тексте.

## 6. Что не сработало и почему

1. **Сниппет вместо текста.** Поиск отдаёт модели 1–2 предложения. Нужное место в них есть в 25% случаев
   (п. 5.8). Модель при этом видит номер записи и резюме «по теме» — и считает, что материал у неё есть.
2. **Наращивание на усмотрение модели при низком усилии.** При усилии low модель читает запись в 43% вопросов
   вместо 82% (п. 5.6). Лестница есть, но подниматься по ней некому.
3. **«В книге нет» после одного поиска.** Правило промпта велит при отсутствии ответа остановиться и не
   собирать ответ из соседних записей (`prompts/system.md:60–64`). В паре с пунктом 1 это даёт ложные отказы:
   8 из 15 провалов, ни в одном запись не открыта (п. 5.5).
4. **Тихая обрезка результата.** 12 000 знаков режут 9 записей из 20 (п. 5.10). Два провала — прямое
   следствие.
5. **Граф.** Противоречий в нём нет, потому что разметчик видел только резюме. Соседи не добавляются из-за
   условия «свободные места». Вклад — 5 записей из 633 (п. 5.9).
6. **Веса названия.** Название ×5 и надбавка +0,3 рассчитаны на содержательные названия. В этой базе
   названия — номера глав (п. 2).
7. **Контроль качества поиска мерил не то.** «Запись в шестёрке — 91%» и «120 лексических зондов — 100%»
   (п. 5.1) оба проходили, пока место доходило до модели в 57% случаев.
8. **Одна переформулировка на вопрос с двумя сторонами.** Запрос маршрутизатора находит вторую сторону хуже,
   чем сам вопрос (0,57 против 0,75, п. 5.7).
9. **Опыт с профилями на 40 вопросах.** Просадку списали на шум и включили профили. На 100 вопросах это
   минус 14 пунктов (п. 5.6).
10. **План починки целился мимо.** `BACKLOG.md:23–24` предлагает «шире поиск: больше `kb.limit`, соседи».
    Но нужная запись и так была возвращена в 54 случаях из 60. Узкое место — не ширина поиска, а доставка
    текста. Второй пункт того же плана — обязательный второй поиск перед отказом — верный.

Чего донор не пробовал вовсе: векторный поиск («A vector database or an embedding provider» — вне первой
стадии, `SPEC.md:26`; шов `Retriever` «позволит pgvector позже», `SPEC.md:33, 267`; в `DECISIONS.md` о
векторах ни слова), нарезку мельче половины главы, переранжирование кандидатов моделью для базы знаний
(оно есть только для памяти, `DECISIONS.md:264`), слой самоулучшения (только спецификация,
`SPEC.md:564–617`).

## Как воспроизвести мои замеры

Все замеры бесплатные и детерминированные; базы открывались только на чтение
(`file:…?mode=ro&immutable=1`), в проекты ничего не записано.

1. Загрузить модули донора по пути к файлу, без пакета и настроек: `src/mentor/stemming.py`,
   `src/mentor/kb/box.py`, `src/mentor/kb/search.py`. Нужен интерпретатор донора (`.venv/bin/python`, в нём
   стоит `snowballstemmer`), запуск с `PYTHONDONTWRITEBYTECODE=1`.
2. Из `data/eval/<прогон>.sqlite` взять `eval_results` + `turns`: `router_json.kb_query`,
   `flags_json.retrieved.kb`, `tool_calls_json`, `scores_json.reply`, `passed`.
3. Повторить предпоиск: `search_box(conn, box_id, box, kb_query, user_id=None, limit=3, neighbours=True,
   quote_max_lines=2)`; сверить номера с журналом (должно совпасть 95 из 95).
4. Повторить каждый `kb_search` агента с его запросом и `limit`; для `kb_unit full` собрать ту же строку
   JSON, что `runtime/tools.py:153–175`, и обрезать на 12 000 знаков.
5. Показанный текст = цитаты и резюме из шагов 3–4 плюс текст открытых записей. Место показано, если самая
   длинная общая цепочка слов золотой цитаты (`evals/golden/cases.jsonl`, поле `support[].quote`) с
   показанным текстом — не меньше 60% длины цитаты.
6. Что-если по кускам: разрезать тексты записей по границам предложений на куски заданного размера, построить
   FTS5 по основам в памяти, искать тем же OR-запросом.
