### 1.5. Честная сводка по «узкому месту» [агент]

Зафиксированная позиция владельца: синтетик **производит вопросы и диалоги**, приборы дают замер
«ступени 2», а финальное суждение — за человеком, на малой выборке (20–30 вопросов, ~30 пар), по
узнаванию. Требование «убрать владельца из оценки» — пока не записанное решение, а тема открытого
вопроса №1 концепта. Проектировать новый контур стоит так: автоматика отсеивает и ранжирует,
владелец калибрует судью на ~30 парах вслепую; расхождение судьи с владельцем — измеряемая величина.

## 3. Механика прогона

### 3.1. `participant_core` (то, что реально исполнялось в SU)

```
TurnSource (сценарный) → гейт вопроса → Transport.send → readReply (регулярки) → decideNext
```

- **Кто ведёт разговор**: никакая модель. Источник реплик всегда сценарный
  (`SU/bounded_contexts/participant_core/scripts/run-scenario.mjs:76`); «живой» источник бросает
  исключение «not wired» (`actor.mjs:134-149`) и из командной строки недостижим. [П]
- **Решения актёра**: advance / press / clarify / leave_satisfied / leave_unsatisfied / stop_*
  (`actor.mjs:27-36`). «Press» повторяет вопрос дословно (`actor.mjs:103-112`). [П]
- **Канал**: `LocalTransport` вызывает функцию-обработчик в том же процессе
  (`transport.mjs:69-125`). `TelegramTransport` написан на Bot API (`sendMessage` + опрос
  `getUpdates`), живьём не запускался, `verified_live:false` (`transport.mjs:145-290`). Замечание:
  `getUpdates` у живого бота запрещён общим правилом владельца. [П]
- **Как адресуется цель**: `--target <module.mjs>`, модуль экспортирует
  `handler(text, context) → string | {text, meta} | Promise` (`run-scenario.mjs:137-146`;
  `participant_core/README.md:69-76`). Единственный адаптер — `SU/targets/aichattg-assistant.mjs`:
  запускает дочерним процессом локальный стенд ассистента
  `/Users/alexeykrolmini/Code/AIchatTG/apps/telegram-runtime/scripts/local-assistant.mjs`
  (строки 60-70), платный режим — `SU_TARGET_LIVE=1` (98-104). [П]
- **Оркестрация**: один план = один процесс; параллелизма, расписания, пакетного запуска нет
  («Does not own… traffic scheduling, concurrency», `participant_core/README.md:175-177`). [П]
- **Контроль расхода**: только `maxTurns` и терпение; флаг `--authorized` для планов с
  `requires_explicit_authorization` (`run-scenario.mjs:56-61`). Денег и токенов журнал не считает
  (`journal.mjs:86-117`). [П]
- **Журнал**: `runs/<run_id>/{run.json, transcript.jsonl, decisions.jsonl, rejected_turns.jsonl,
  conversations.jsonl}`, производная, в git не идёт. [П]

### 5.3. Дефекты стенда, искажавшие или способные исказить результат

Найдено по коду и данным SU: [П]

1. **Улики цели выбрасываются.** `LocalTransport` берёт из ответа обработчика только `text` и
   `meta` (`transport.mjs:112-116`), а адаптер кладёт маршрут, воздержание, модель и цену в поле
   `evidence` (`targets/aichattg-assistant.mjs:79-90`). Во всех 125 ходах мета содержит лишь
   `is_measured_target, mode, transport`. Сухой прогон неотличим от живого. Подтверждено владельцем
   проекта-наследника: «иначе журнал прогонов лжёт» (`agi/REGISTRY.md:950`).
2. **Цена не дошла бы и после починки.** Адаптер читает `last.costUsd` и `last.tokens`
   (строки 87-88), а стенд вкладывает их в объект `cost`, причём `costUsd` там намеренно пуст.
3. **Переигрывание истории.** Адаптер на каждый ход запускает стенд заново на всём диалоге
   (строки 32-39, 54-58): N ходов = 1+2+…+N генераций, а ранние ответы пересоздаются — память цели
   может расходиться с тем, что синтетик реально прочитал.
4. **Ложное «уточнение».** Маркеры уточнения — подстроки по длинному ответу: «Уточните это у

   при этом `clarify` поведения не меняет: отправляется следующий сценарный ход.
5. **Скрытая ошибка решения.** Ответ с маркерами и отказа, и уточнения: `usable:false`, но

6. **Чтение ответа настроено на одну цель.** Первый живой прогон: пять воздержаний подряд прочитаны

7. **Сценарные продолжения предполагают ответы прежнего бота** — они не адаптивны; `press`

8. **Общий экземпляр цели на процесс** (`handler._target`, строки 98-104): несколько планов в одном

### 6.2. Контракты, которым должна удовлетворять тестируемая система

- **Шов цели**: ESM-модуль с `handler(text, context)`; возвращает строку или `{text, meta}`;
  молчание — `text: null`; сбой канала — исключение `TransportError` (с `retryable`), сбой никогда
  не записывается как ответ (`transport.mjs:1-28`; `actor.mjs:278-287`). [П]
- **Контекст**: `{conversation_id, turn_index}` — цель сама держит сессию по `conversation_id`. [П]
- **Улики**: маршрут, признак воздержания, модель, токены, цена — в `meta` (не в `evidence`),
  пока транспорт не исправлен. [П]
- **Описание цели**: `describe()` с `is_measured_target`, режимом и `verified_live` — чтобы прогон
  на заглушке нельзя было принять за замер (`participant_core/README.md:78-80`). [П]
- **Для оценки** (схема `dialogue_eval`): на каждый ход — заранее записанное ожидание
  `{behavior, note}`; стенограмма `kb_dialogue_transcript_v1`. [П]

### 6.3. Что нужно, чтобы синтетики вели (а) удалённый сервис ответов по HTTP/MCP [агент]

1. Модуль-цель: `handler` делает запрос к сервису (HTTP POST или вызов инструмента MCP), хранит
   карту `conversation_id → идентификатор сессии сервиса`, пустой ответ отдаёт как `null`, сетевой
   сбой — `TransportError`. Объём — десятки строк.
2. Экземпляр цели — на диалог, а не на процесс (дефект 8).
3. Сервис возвращает в ответе машинные улики: какие записи базы использованы, было ли
   воздержание, модель, токены; обработчик кладёт их в `meta`.
4. Сессия на стороне сервиса, без переигрывания истории (дефект 3).
5. Удалённый вызов — платный и внешний: нужен бюджет и потолок на прогон в коде, счётчик денег в
   журнале (сейчас его нет).

### 6.4. …и (б) дженерик-чат с плагином (Claude Code без интерфейса) [агент]

1. Модуль-цель запускает дочерний процесс CLI в неинтерактивном режиме на каждый ход, с
   продолжением той же сессии (а не с переигрыванием истории) и машинным выводом; из вывода берёт
   итоговый текст, идентификатор сессии, расход и токены → `text` + `meta`. Точные флаги сверить по
   `claude --help` установленной версии — по памяти их не фиксирую.
2. Изоляция: отдельная рабочая папка без проектных инструкций, фиксированная модель, плагин
   подключён явно, инструменты ограничены плагином — иначе меряется окружение, а не плагин.
3. Синтетику показывать ответ целиком (дефект 10) и не передавать служебный вывод инструментов.
4. Это платные вызовы — те же потолки и учёт, что в 6.3.

### 6.5. Общее для обоих случаев [агент]

- **Парное сравнение требует одинакового потока вопросов.** Со сценарным источником это даётся
  даром; с живым синтетиком диалоги расходятся после первого хода. Поэтому: одноходовые вопросы и
  сценарные многоходовки с самодостаточными продолжениями — для парного сравнения двух целей;
  адаптивные диалоги — отдельным замером на уровне траектории.
- **Слепота против эталона.** Вопрос с ожидаемым ответом пишет проектировщик, видящий базу
  (офлайн, один раз, файлом); синтетик в рантайме базы не видит. Не смешивать.
- **Чтение ответа регулярками не переносить.** Признак воздержания брать из улик цели, а
  удовлетворённость персоны — отдельным узким модельным суждением с проверкой цитаты кодом.
- **Живой источник реплик** проще взять из `agi` (рендер роли + экземпляр), чем достраивать слот в SU.
- **Судья содержания** — главный недостающий прибор: без проверки ответа против записей базы
  повторится дыра раздела 4.2. Для сервиса ответов по базе она закрывается естественнее, чем для
  бота курса: ожидание можно привязать к идентификаторам записей.
- **Калибровка**: ~30 пар вслепую оценивает владелец (как в шаге К2), судья — те же пары; доля
  расхождений — число, по которому решается, можно ли судье доверять остальное.
