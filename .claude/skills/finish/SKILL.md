# Skill: Finish Session

## Главный контракт

`/finish` не превращает красный или непроверенный кандидат в нормальный
коммит. Сначала проверка, затем коммит. Ошибка теста сохраняется с исходным
exit status и именами упавших проверок; её нельзя скрывать через `|| true`,
переписывать как `passed` или обходить «временным» коммитом.

## 1. Зафиксировать исходную границу

До любых действий:

```bash
git status --short
git diff --stat
git diff --cached --stat
```

Отделить изменения текущей задачи от уже существовавших пользовательских
изменений. Не stage и не commit чужие пути.

## 2. Запустить релевантные тесты

Для этого проекта основная команда запускается под поддерживаемым Node 20.20.x:

```bash
env PATH=/Users/alexeykrolmini/.nvm/versions/node/v20.20.0/bin:$PATH npm test
```

Для узкого изменения сначала можно запустить целевой тест, но перед коммитом
кандидата всё равно нужен полный `npm test`, если только технически невозможно
его выполнить. Команду запускать без подавления exit status.

Если тесты падают:

1. Сохранить точную команду, exit status и список ошибок.
2. Попробовать исправить причину и повторить проверку не более трёх раз.
3. Если тесты остаются красными — остановить `/finish` до staging/commit.
4. Доложить `failed`; при проблеме окружения — `inconclusive`; не называть это
   `passed` и не коммитить кандидат как завершённый.

Локальный session log можно дополнить результатом падения, но нельзя менять
tracked SNAPSHOT/BACKLOG так, чтобы затем случайно закоммитить красный
кандидат.

## 3. Проверить дифф после зелёных тестов

```bash
git status --short
git diff --check
git diff --stat
```

Проверить каждый путь по `.claude/rules/commit-policy.md`. Секреты, production
данные и чужие изменения не stage. Использовать только `git add -- <точные
пути>`; `git add .`, `git add -A` и `git add -u` для всего worktree запрещены.

## 4. Закоммитить проверенный кандидат

Сформировать описательный commit message и закоммитить только названные пути.
Если commit завершился ошибкой — сохранить и сообщить ошибку; не маскировать её
и не утверждать, что кандидат закоммичен.

## 5. Обновить state-слои

Только после успешных тестов и продуктового коммита привести в соответствие:

- `.claude/SNAPSHOT.md` — текущее состояние и дата;
- `.claude/BACKLOG.md` — оставшаяся работа;
- `.claude/INVARIANTS.md` — только новые или изменённые жёсткие контракты;
- `.claude/ARCHITECTURE.md` — только фактические изменения карты системы.

Перед staging выполнить:

```bash
scripts/framework-state-mode.sh check-safe-mode
FRAMEWORK_STATE_COMMIT="$(scripts/framework-state-mode.sh should-commit-framework-state)"
```

В `private-solo`, если `FRAMEWORK_STATE_COMMIT=true`, добавить только реально изменённые
state-файлы поимённо и закоммитить их. В `public`/`private-shared` они остаются
локальными. Ошибка helper — blocker, а не повод продолжать.

## 6. Сохранить диалог

```bash
if [ -f scripts/save-dialogs.sh ]; then
  bash scripts/save-dialogs.sh
fi
```

Если сохранение завершилось ошибкой, сообщить её отдельно; не скрывать.

## 7. Отчёт

Сообщить:

- что сделано;
- тестовую команду и статус (`passed` / `failed` / `not_run` /
  `inconclusive`);
- хэши реально созданных коммитов;
- что осталось и требуется ли Product Owner attention gate.

Push и production-действия выполняются только когда они явно разрешены
пользователем и соблюдены project-specific production gates.

## Чего не делать

- Не коммитить при `failed` или `inconclusive` проверке кандидата.
- Не подавлять ошибки тестов, helper-скриптов, сохранения или commit.
- Не stage весь worktree.
- Не выдавать commit, push или локальный тест за deployment evidence.
