# Правило: Управление контекстом

## Проблема

Деградация контекста начинается при 50-60% заполнения окна. При compaction агент теряет детали и может повторять уже выполненную работу или ломать код.

## Превентивные меры

### Регулярная фиксация состояния

После каждого значимого блока работы (не реже чем каждые 20 tool calls — совпадает с checkpoint hook):
- Проверить: есть ли незакоммиченные изменения
- Если да: проверить границы владения и релевантные тесты
- Коммитить только осознанно выбранные пути и только после зелёной проверки
- Обновить SNAPSHOT.md после успешного коммита, если изменилось состояние проекта

### Признаки деградации контекста

Если замечаешь у себя:
- Повторяешь ранее обсуждённое
- Не помнишь, что было сделано в начале сессии
- Путаешь файлы или структуру проекта

**Немедленно:**
1. Перечитай `.claude/SNAPSHOT.md`
2. Перечитай `CLAUDE.md`
3. Проверь `git log --oneline -20` для восстановления хронологии

### Не теряй границы незакоммиченных изменений

Большой объём незакоммиченных изменений = риск смешать задачи при compaction.
Держи явный список принадлежащих задаче путей и делай атомарные коммиты после
проверки. Compaction сам по себе не даёт полномочий stage/commit.

## Pre-Compaction протокол

Перед compaction автоматически срабатывает hook `PreCompact`, который:

1. Проверяет совместимость `repo_access` с tracked framework paths.
2. Печатает read-only `git status` checkpoint.

**Что hook НЕ делает:**
- Не stage и не commit никакие пути.
- Не обновляет timestamp или содержательные секции SNAPSHOT.
- Не скрывает unsafe `repo_access`: возвращает blocker status.

Поэтому содержательный checkpoint делается агентом на безопасной границе задачи,
а не автоматикой и не обязательно ровно перед compaction.

## Post-Compaction протокол

После compaction (автоматически через hook `PostCompact`):

1. **Перечитать SNAPSHOT.md** — восстановить понимание состояния
2. **Перечитать CLAUDE.md** — восстановить контекст проекта
3. **git log --oneline -10** — проверить хронологию коммитов
4. **Не начинать новую работу** пока не восстановлен контекст

## Правило для длинных сессий

При работе более 30 минут:
- На безопасных границах: проверка + атомарный коммит + обновление SNAPSHOT
- Перед каждой крупной задачей: проверить актуальность SNAPSHOT
- После каждого субагента: принять результат, проверить и только затем commit + SNAPSHOT
