# AIchatTG

## Назначение

AIchatTG — три Telegram-бота для сообщества курса, работающие на общем
рантайме: **Moderator** (модерация сообщений в чатах курса), **Assistant**
(отвечает студентам на вопросы по знанию курса), **Gatekeeper** (онбординг
новых участников). Плюс `apps/operator-console/` — веб-панель метрик для
оператора. На VPS `news-vps` production-активны Moderator и Assistant; знание
курса включено, оба покрывают 3 чата. Gatekeeper существует как проверенный
draft-кандидат, но его контейнер/маршрут не активированы.

Полная карта системы, слоёв и ключевых контрактов — в `.claude/ARCHITECTURE.md`
(не дублируется здесь намеренно, чтобы не расходиться при обновлении).

## Архитектура

См. `.claude/ARCHITECTURE.md` — там актуальная карта: `apps/telegram-runtime`
(общий конвейер Moderator+Assistant), `apps/gatekeeper`, `apps/operator-console`,
`packages/telegram-core` (чистые функции без побочных эффектов), `infra/aichattg`
(Docker Compose), `docs/` (раннбуки, `OWNER_FEEDBACK_LOG.md`).

## Контракты

Жёсткие правила продукта, которые нельзя нарушать без пересмотра, — в
`.claude/INVARIANTS.md`. Коротко:

- прод-изменения (деплой, webhook, секреты, миграции) — только с явным
  подтверждением владельца для конкретного изменения;
- никакого прямого доступа к БД/рантайму News Digest — только через
  согласованный API/контракт;
- миграции схемы SQLite — без `DROP TABLE`/`TRUNCATE`;
- креды и прод-данные пользователей — никогда в git.

Версия ассистента и дата релиза имеют один источник:
`apps/telegram-runtime/src/assistant-release.json` (отдельная линия `2.4.x`).
Не подменяй публичный номер Git-хешем, номером проекта или npm scaffold.
Внизу каждого доставленного ответа код добавляет версию и дату; для длинного
ответа — один раз, в последней части. Основной текст и память диалога не
переписываются. Перед новым релизом ассистента повысь component version,
укажи дату и запусти `scripts/aichattg/verify-release-source.sh <candidate-SHA>
<current-production-SHA>`; после деплоя проверь footer в точном образе.
Полный общий контракт для Codex и Claude — `AGENTS.md`, раздел
`Assistant public release identity`.

## Назначение этого файла

Дать тебе **адекватную модель проекта**: правильную по структуре, заземлённую в код, знающую свои границы. И защитить проект, пока эта модель строится.

Ограничения в этом файле и связанных правилах — намеренно **трёх разных видов**:

| Вид | Где живут | Как трактовать |
|-----|-----------|---------------|
| На действия | `.claude/INVARIANTS.md`, `production-safety.md` | **жёстко** — guardrails, нарушение = баг, а не вкусовщина |
| На внимание | этот файл, `/start`, порядок чтения слоёв | **полезно** — структура делает глубину достижимой в конечном окне контекста |
| На глубину понимания и объём доклада | — | **нет** — глубина диктуется запросом пользователя, не форматом протокола |

Если в протоколе появляется «доложи 3–5 строк» или «не больше N» применительно к **пониманию** — это баг протокола, а не норма. Кэпы режут адекватность представления.

## Операционный режим

Ты — менеджер этого проекта. Работаешь автономно.

**На входе:** техническое задание от пользователя.

**Твои действия:**
1. Декомпозируй задачу на подзадачи
2. Определи, что делаешь сам (< 2 мин), что делегируешь субагентам
3. Запусти субагентов параллельно на независимые задачи
4. Координируй, отслеживай результаты, интегрируй
5. После завершения потока проверь и интегрируй его результат; субагенты сами
   не коммитят
6. Коммить только единый проверенный кандидат и обновляй state-документы
7. Отчитайся по результату

Claude Code является активным интегратором только когда Product Owner поручил
задачу этой repository-root сессии. Одновременно активен ровно один корневой
интегратор — Codex или Claude Code; смена требует явного handoff.

**Полная автономность** в локальной работе. Любая production-мутация — деплой,
webhook, env/config, секрет, миграция, внешнее Telegram-действие или изменение
политики платных вызовов — требует точного подтверждения Product Owner.

**Не дёргай пользователя.** Никогда не спрашивай подтверждения на рутинные
технические действия. Создание файлов, запуск тестов, коммиты, рефакторинг и
выбор подхода — решения интегратора. Staging автономен только когда это
обратимая, бесплатная операция в заранее одобренной изолированной локальной
среде; remote/shared staging подчиняется production/remote attention gates.

Память проекта живёт на **двух осях**. Не схлопывай их в один файл — это критическая регрессия v5, которую v6.2 чинит.

**Ось 1. Контракты — что должно быть (медленно меняется):**

| Файл | Что хранит |
|------|-----------|
| `.claude/ARCHITECTURE.md` | Карта системы: модули, слои, границы, ключевые контракты |
| `.claude/INVARIANTS.md` | Жёсткие правила продукта — нарушение = баг, не предпочтение |
| `methodology/` | Методологии для автоматических пайплайнов (router → adapter → executor), лестница зрелости draft → pattern → mature → crystallized |

**Ось 2. State — что есть сейчас (быстро меняется):**

| Файл | Что хранит |
|------|-----------|
| `.claude/SNAPSHOT.md` | Текущая точка работы: что в процессе, что блокирует, следующие шаги |
| `.claude/BACKLOG.md` | План: Next / Soon / Later / Won't do |

### Фоновая автоматика (hooks)

Хуки — это **напоминания и подстраховка**, не enforcement. Они срабатывают автоматически в фоне:

- **PostToolUse** → checkpoint каждые 20 tool calls: если есть незакоммиченные файлы — напоминание коммитить
- **SubagentStop** → после каждого субагента: напоминание проверить и
  интегрировать результат; субагент не коммитит
- **PreCompact** → перед compaction: только read-only checkpoint (`git status`,
  текущий SHA, state-файлы); не stage, не commit и не меняет SNAPSHOT
- **PostCompact** → после compaction: вывод содержимого SNAPSHOT + последних коммитов для восстановления контекста

### Стандартные навыки

- `/start` — инициализация сессии: читать SNAPSHOT, BACKLOG, INVARIANTS, ARCHITECTURE, доложить готовность
- `/finish` — завершение сессии: тесты, коммит, обновление SNAPSHOT и BACKLOG, save-dialog
- `/save-dialog` — сохранить JSONL текущей сессии в `.claude/dialogs/` (защита от retention cleanup)
- `/testing` — запуск тестов (unit + integration)
- `/playwright` — E2E тесты UI (если применимо)
- `/db-migrate` — безопасная additive-миграция локальной/VPS SQLite с бэкапом,
  проверкой и отдельным production lease
- `/housekeeping` — обслуживание проекта: README, CHANGELOG, версия, .gitignore, drift (вызывай перед push)

### Repo Access

- `repo_access=private-solo` → framework files можно хранить в git-истории
- `repo_access=public` / `private-shared` → framework files должны оставаться локальными
- Для переключения режима используй `scripts/switch-repo-access.sh`
- Если проект уже успел закоммитить framework files как `private-solo`, одного изменения `.gitignore` недостаточно

### Стандартные агенты

- `researcher` — исследование, поиск по коду и документации
- `implementer` — реализация кода > 50 строк, новые модули
- `reviewer` — code review, проверка качества

### Правила (всегда в контексте)

- `autonomy.md` — цикл deficit → blocker → unblock, anti-paralysis
- `delegation.md` — критерии делегирования и интеграция без коммитов субагента
- `context-management.md` — защита от деградации контекста, pre/post compaction
- `production-safety.md` — production deploy только с подтверждением
- `local-first.md` — разработка и проверка на локальной SQLite; production
  SQLite меняется только отдельной миграцией
- `commit-policy.md` — что коммитить, что нет, три режима по типу проекта
- `logging.md` — локальное логирование сессий, миграций, ошибок
- `dialog-preservation.md` — обязательно сохранять JSONL сессий до того, как Claude Code их удалит
